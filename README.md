# 파일 형식 구조 시각화

바이너리 문서 형식의 내부 구조를 **실제 바이트로** 뜯어 보는 교육용 인터랙티브 자료.
두 편으로 되어 있고, 뒤 편은 앞 편 위에 얹힌다.

| 편 | 다루는 것 | 빌드 결과 |
|---|---|---|
| **CFB 편** (`index.html`) | MS-CFB 컴파운드 파일 — 섹터·FAT·DIFAT·디렉터리 트리·미니 스트림 | `dist/cfb-visualizer.html` |
| **HWP 편** (`hwp.html`) | HWP 5.0 — FileHeader·압축·레코드 구조·레벨 트리·글자 추출 | `dist/hwp-visualizer.html` |

`.hwp`는 그 자체가 CFB 컨테이너다. 그래서 HWP 편은 CFB 엔진을 그대로 재사용하고,
그 위에 한글이 얹은 것만 다룬다.

---

## CFB 편

MS-CFB(Compound File Binary Format, 흔히 OLE2 / Structured Storage)의 내부 구조를
**실제 바이트로** 뜯어 보는 교육용 인터랙티브 자료.

`.doc`, `.xls`, `.ppt`, `.msi`, `.msg` 같은 파일 안에는 폴더와 파일, 할당 테이블,
빈 공간, 그리고 지워졌지만 남아 있는 데이터가 들어 있다. 파일 하나 안에 파일시스템이
통째로 들어간 셈이다. 이 자료는 그 구조가 어떻게 잡혀 있는지, 읽을 때와 쓸 때
무슨 일이 벌어지는지를 단계마다 보여 준다.

## 그림이 아니라 진짜 파일이다

이 페이지의 핵심 설계 원칙은 **아무것도 흉내 내지 않는다**는 것이다.

1. 브라우저가 실행되면 `src/cfb-build.js`가 **진짜 CFB 파일을 바이트 단위로 만든다**
   (실제 Word 97 문서의 구조를 본뜬 27 KiB짜리 v3 파일). 그리고 곧바로
   **일곱 단계의 편집을 실제로 가한다** — 갓 만든 파일은 모든 체인이 0,1,2,3…으로
   이어져 있어서 보기에는 좋지만 거짓말을 가르치기 때문이다. 편집을 거친 샘플은
   앞뒤로 튀는 체인, 가운데가 뚫린 미니 스트림, 흩어진 미니 스트림 그릇,
   옛 데이터가 남은 빈 섹터, 이전 세입자의 흔적이 보이는 슬랙을 모두 갖는다.
2. `src/cfb-parse.js`가 그 바이트를 **아무 사전 지식 없이 처음부터 파싱한다.**
   파서는 결과만이 아니라 "무엇을, 왜, 어느 오프셋에서 읽었는가"를 단계로 기록한다.
3. 화면의 모든 패널 — 섹터 지도, hex 뷰, 체인 다이어그램, 트리 — 은 그 **하나의
   파싱 결과**를 공유한다. 그래서 어떤 패널이 "이 값은 0x2C에 있다"고 말하면,
   hex 뷰에서 그 바이트를 직접 볼 수 있다.
4. 쓰기 실습실의 모든 연산(삭제·추가·크기 변경·조각 모음)은 **실제 바이트를 다시
   쓰고**, 그 결과를 파서가 처음부터 다시 읽는다. 시뮬레이션이 아니다.

스트림 내용도 아무 값으로 채우지 않았다. 각 섹터를 열면 hex 뷰의 아스키 열에
`[WordDocument +0x001A00]` 처럼 **자기가 어느 스트림의 몇 번째 바이트인지**가
그대로 읽힌다. 체인을 따라갈 때 "정말 이 섹터가 맞나"를 눈으로 확인할 수 있다.

자기 컴퓨터의 진짜 `.doc` / `.xls` / `.msi` / `.msg` 파일을 끌어다 놓으면
모든 패널이 그 파일을 대상으로 다시 그려진다. 파일은 브라우저 안에서만 읽히고
어디로도 전송되지 않는다.

## 다루는 내용

| 장 | 내용 |
|---|---|
| 0x00 | 왜 파일 안에 파일시스템을 넣었나 — 복합 문서 문제와 평평한 파일의 한계 |
| 0x01 | 512바이트 헤더를 필드 하나씩 (헤더의 85%가 DIFAT인 이유) |
| 0x02 | 섹터와 주소 계산 `(n+1) × 섹터크기`, 특수 섹터 값 여섯 개 |
| 0x03 | FAT — 스트림은 연결 리스트다. 체인 따라가기 |
| 0x04 | DIFAT — 표를 가리키는 표. 3단 간접 참조와 "왜 하필 109인가" |
| 0x05 | 디렉터리 — 128바이트 엔트리와 레드-블랙 트리, 이름 정렬 함정 |
| 0x06 | 미니 스트림 — 작은 파일들의 아파트, 2단계 주소 변환 |
| 0x07 | 읽기 — 파서가 실행한 21단계를 그대로 재생 |
| 0x08 | 쓰기 — 단편화는 왜 생기고, 지운 데이터는 왜 남는가 |
| 0x09 | 실전 — 내 파일 열어 보기, 보안·포렌식에서의 의미 |
| 0x0A | 부록 — 상수표, 범위 잠금 섹터, 구현할 때 넘어지는 지점 17가지 |

## 실행

정적 파일뿐이라 서버가 필요 없다.

```bash
# 개발 — 모듈이 나뉜 상태 그대로 연다
python3 -m http.server 8000     # 그리고 http://localhost:8000

# 배포용 단일 파일 만들기 (CSS·JS 전부 인라인)
node build.mjs                  # → dist/cfb-visualizer.html

# 엔진 검증
node test.mjs
```

`dist/cfb-visualizer.html`은 자체 완결적이다. 외부 요청은 Google Fonts 하나뿐이고,
글꼴을 못 받아도 시스템 글꼴로 정상 동작한다.

## 색 규칙

섹터 색은 세 계열뿐이고, 그것이 곧 이 포맷의 요약이다.
CFB 파일의 모든 바이트는 **주소이거나, 이름이거나, 내용**이다.

| 계열 | 색 | 무엇 |
|---|---|---|
| 주소표 | 파랑 | FAT (단색) · DIFAT (빗금) · MiniFAT (점) |
| 이름표 | 주황 | 디렉터리 섹터 |
| 내용 | 청록 | 일반 스트림 (단색) · 미니 스트림 (빗금) |
| 빈 곳 | 회색 | 비어 있음 — 다만 안의 바이트는 남아 있을 수 있다 |

계열 안의 구분은 색이 아니라 **무늬**로 한다. 색만으로 뜻을 전달하지 않도록
구역마다 이름표를 직접 붙이고, 범례와 구역 표를 항상 제공한다.
세 색은 색각 이상 조건에서도 구분되도록 검증했다
(all-pairs CVD ΔE ≥ 9.2, 일반 시야 ΔE ≥ 20.9, 명·암 테마 양쪽).

## 검증

`node test.mjs`는 760개 검사를 돌린다 (CFB + DEFLATE + HWP).

- v3 / v4 파일 생성 → 파싱 왕복
- 편집(삭제·추가·확대·축소·조각 모음) 후 매번 불변식 확인
  - 모든 스트림이 루트에서 도달 가능한가 (트리에서 미아가 생기지 않는가)
  - 섹터가 두 체인에 동시에 속하지 않는가
  - 체인 길이가 스트림 크기와 맞는가
  - 각 저장소의 자식 트리가 **유효한 레드-블랙 트리**이고 CFB 이름 순서로 정렬되는가
  - 모든 스트림 내용이 바이트 단위로 보존되는가
- 손상된 입력 방어: 순환하는 FAT 체인, 잘린 파일, ZIP 파일
- 재현 가능한 시드로 무작위 손상 400회 퍼징 — 예외 없이 처리
- 편집된 샘플이 교재로서 갖춰야 할 성질을 실제로 갖추는지 (튀는 체인, 끊긴 미니 체인,
  흩어진 그릇, 유령 데이터, 슬랙, 미할당 디렉터리 칸)
- DEFLATE 왕복 + 손상 입력 200건
- HWP: 압축 켠/끈 두 경우 모두 만들기 → 읽기 왕복, 레코드 머리 비트 재조립 일치,
  확장 헤더 등장, 레벨 트리 부모-자식 관계, 제어 문자 폭 합계 = 레코드 크기,
  표 안의 글자까지 추출
- HWP 샘플 충실도: 모든 문단에서 `글자 수 × 2 = PARA_TEXT 크기`, 압축 꼬리의 CRC-32와
  원본 길이 일치, DocInfo 정의가 ID_MAPPINGS 아래 레벨 1, 표 칸의 문단이 LIST_HEADER의
  형제, CTRL_HEADER가 디스크에 뒤집혀 저장됨
- HWP 쓰기: 4095바이트 내용이 확장 헤더를 쓰는지(`>=` 대 `>`), 파생 값을 빠뜨렸을 때
  파일이 "열리면서도" 어긋나는지

## HWP 편

HWP 5.0을 읽는다는 것은 **서로 다른 세 형식을 차례로 통과**한다는 뜻이다.

```
.hwp 파일
  └ 1층: CFB 컴파운드 파일        ← .doc 와 같은 껍데기 (CFB 편에서 다룸)
      └ 2층: raw DEFLATE 압축     ← zlib 헤더도 검사값도 없다
          └ 3층: 레코드 스트림     ← 4바이트 머리에 태그·레벨·크기를 접어 넣는다
```

핵심은 3층이다. 레코드 머리 4바이트를 리틀엔디언 32비트로 읽으면
**태그 10비트 + 레벨 10비트 + 크기 12비트**가 겹치지 않게 들어 있다 (`10+10+12=32`).
그리고 트리를 만드는 데 포인터를 하나도 쓰지 않는다 — **레벨 숫자와 등장 순서만으로** 세운다.
CFB 디렉터리가 `left`/`right`/`child` 포인터로 트리를 그려 두는 것과 정반대다.

| 장 | 내용 |
|---|---|
| 0x00 | 세 겹의 상자 — 왜 컨테이너 안에서 또 압축하고, 또 구조를 만드나 |
| 0x01 | FileHeader 256바이트 — 두 번째 서명, 속성 비트 18개 |
| 0x02 | 스트림 구성 — 무엇이 압축되고 무엇이 평문인가 |
| 0x03 | 압축 층 벗기기 — raw DEFLATE, 검사값 없음의 대가 |
| 0x04 | 레코드 머리 — 4바이트 비트 쪼개기 (슬라이더로 직접 만들어 보기) |
| 0x05 | 레벨 — 포인터 없이 세우는 트리 |
| 0x06 | 레코드 해부 — 이름 대신 등장 순서로 가리키기 |
| 0x07 | 글자 뽑기 — 여덟 자리를 차지하는 제어 문자 |
| 0x08 | 읽기 워크스루 — 파서가 실제로 밟은 여덟 단계 |
| 0x09 | 쓰기 — 읽기의 거울이 아니다. 4095 경계, 아무도 검사 안 하는 파생 값 |
| 0x0A | 실전 — 내 .hwp 열기, 배포용 문서, 보안 · 0x0B 부록 |

### 명세 밖의 것들

교차 검증에서 나온, 명세에는 없지만 실제 파일에는 있는 것들도 반영했다.

- **압축 스트림 뒤의 8바이트 꼬리** — CRC-32(LE) + 원본 길이(LE). gzip 꼬리에서 머리만 뗀 모양이다.
  명세에 한 줄도 없고, `inflate`가 마지막 블록에서 멈추므로 읽는 쪽은 대개 보지도 않는다.
  그래서 "raw deflate라 검사값이 없다"는 설명이 널리 퍼졌지만 사실이 아니다 —
  **검사값은 있고, 아무도 안 본다.** 작성기가 이 꼬리를 쓰고, 파서가 검증해서 화면에 보여 준다.
- **표 칸의 문단은 `LIST_HEADER`의 자식이 아니라 형제다.** 소속은 레벨이 아니라
  `LIST_HEADER`의 문단 개수 필드로 센다 — 레벨 트리가 구조의 전부가 아니라는 뜻이다.
- **`PARA_HEADER`의 글자 수는 최상위 비트가 깃발**이라 `& 0x7FFFFFFF`로 가려야 한다.
- **`CTRL_HEADER`의 네 글자는 디스크에 뒤집혀** 놓인다 (`tbl ` ↔ ` lbt`).
- **배포용 문서에서 `BodyText`는 사라지지 않는다** — `ViewText`가 추가될 뿐이고 둘이 공존한다.

### DEFLATE를 직접 구현한 이유

브라우저의 `DecompressionStream`은 비동기라, "모든 것이 한 프레임 안에서 실제 바이트로
계산된다"는 이 자료의 원칙과 맞지 않는다. 그래서 `src/inflate.js`에 동기 구현을 두었다.

- **inflate** — 저장 블록·고정 허프만·동적 허프만 전부. Node `zlib`이 만든 모든 레벨의
  출력을 정확히 푼다.
- **deflate** — LZ77 + 고정 허프만, 안 줄어들면 저장 블록으로 대체.
  결과를 표준 `zlib`이 그대로 푼다는 것까지 테스트로 확인한다.

```

src/inflate.js        DEFLATE 압축/해제 (의존성 없음)
src/hwp-const.js      FileHeader 필드·속성 비트·태그 표·제어 문자 표

src/hwp-parse.js      계측된 HWP 리더 — 레코드 자르기, 레벨 트리, 글자 추출
src/ui-hwp.js         FileHeader·스트림·압축·비트·트리·레코드·글자 패널
src/main-hwp.js       조립
```

## 출처

**CFB 편** — 마이크로소프트 공개 명세 **[MS-CFB] Compound File Binary File Format**,
그리고 Apache POI POIFS, olefile, SheetJS CFB, Rust `cfb` 크레이트, LibreOffice `sot`.

**HWP 편** — 한컴 공개 명세 **한글문서파일형식 5.0**, 그리고 pyhwp, hwp.js, hwplib.
`.hwpx`/OWPML은 국가표준 **KS X 6101**이다.
